## 背景 / 问题
- 当前本地 `web_demo` 页面可以运行，但本机 `127.0.0.1:8080` 没有可用的 Dify 服务，因此本地问答链路会退回 fallback。
- 用户当前要优先确保“可提交的一版基于 Dify 的实验室安全小助手”先落地，而不是先继续彩排或继续扩展业务功能。
- 现有腾讯云服务器已经具备可用的 Dify 基础环境与 `web_demo` 配置，因此最短路径不是在 Windows 本机重建完整 Dify，而是先把“本地演示入口 + 服务器 Dify 后端”收敛成一套可复用方案。

## 服务阶段
- 当前阶段：Phase 1 - 演示主链路固化（补充本地可落地运行路径）

## 目标
- 提供一套“本地运行 `web_demo`，通过 SSH 隧道接服务器 Dify”的最短落地方案。
- 将这套方案落成可执行脚本，而不是只保留口头命令。
- 补齐最小使用文档和验证说明，确保后续可重复启动、停止和自查。

## 非目标
- 不在本次 change 内重建完整 Windows 本地 Dify 单机环境。
- 不修改 `web_demo` 业务逻辑。
- 不承诺本次直接修复所有问答 fallback 问题。
- 不在本次 change 内推进答辩彩排或最终冻结 Gate。

## 范围
- 包含：
  - `scripts/` 下的本地桥接启动 / 停止脚本
  - `docs/ops/` 下的本地桥接使用文档
  - `README.md` 的快速运行补充
  - `docs/changes/` 当前 change 的 proposal / design / tasks / status / verify
- 不包含：
  - `web_demo/app.py` 业务实现改动
  - 服务器端 Dify 工作流重配
  - 本机 Docker / Dify 全量安装

## 影响面
- 影响模块：
  - 本地启动方式
  - 本地验证方式
  - 文档中的“如何先跑起来”口径
- 影响演示链路：
  - 直接影响“本地是否能以 Dify 口径跑起来”
- 影响发布 / 验证链路：
  - 增加一条最短本地落地路径，但不替代正式 release / prod 验证

## 验收标准
- [ ] 已提供本地接服务器 Dify 的启动脚本
- [ ] 已提供对应的停止脚本
- [ ] 已提供本地桥接落地说明文档
- [ ] 已完成至少 1 次本地启动 + health / meta 验证
- [ ] README 已补充该运行方式入口

## 风险
- 风险 1：该方案依赖服务器可达与 SSH key 可用，不能等同于纯本机单机部署。
- 风险 2：即使桥接成功，Dify 工作流本身仍可能因配置或知识库命中问题回退到 fallback。

## 回退方案
- 回退点：退回当前本地 fallback 运行方式 + 服务器独立运行方式。
- 回退条件：若 SSH 隧道方案在用户机器上不稳定或脚本不可复用。
- 回退步骤：
  1. 停止本地桥接脚本启动的 demo 与 tunnel
  2. 恢复使用当前本地 `python -m uvicorn app:app --host 127.0.0.1 --port 8088`
  3. 如需正式 Dify 版，直接使用服务器 `175.178.90.193:8088`
