# Design

## 目标概述
- 本设计服务于“把项目工作区迁移到 `D:\newwork`，并把 Dify 配置收进项目目录”的目标。

## 方案概要
- 一句话方案：保留旧目录作为回退，复制仓库到 `D:\newwork`，并把 `Dify docker` 配置迁入新仓库内的 `local_env/dify/docker`。
- 主流程：
  1. 在旧仓库建迁移 change
  2. 复制仓库到新工作区
  3. 复制 Dify 配置到新仓库内
  4. 补最小入口说明与脚本口径
  5. 做路径级验证

## 关键决策
- 决策 1：采用“复制迁移”，不直接移动旧目录，降低回退成本。
- 决策 2：Dify 配置统一放入项目内目录，而不是继续放在 `_misc/`。
- 决策 3：先收口最小可用路径，不在本轮批量清洗所有历史绝对路径。

## 影响模块
- 模块 / 文档 / 脚本：`docs/changes/*`、`docs/README.md`（如需要）、`docs/ops/*`（如需要）、本地 Dify 配置目录。
- 影响方式：更新默认工作区口径与 Dify 本地路径。

## 对展示主线的影响
- 对演示链路：统一本地工作区，更利于展示机器上复现。
- 对门禁 / 验证：后续 verify 证据路径需逐步切换到 `D:\newwork`。
- 对答辩材料：无直接影响。

## 风险与取舍
- 风险：旧绝对路径很多，不能一次性完全清理。
- 取舍原因：先保住新路径可用，比一次性全量替换更稳。

## 未决问题
- 问题 1：新项目目录名称最终固定为哪个。
- 问题 2：本地 Dify 的 WSL / Docker 问题是否在新路径下同时继续修。

## 不做项
- 本次明确不覆盖：历史 release 产物批量重写、所有 docs 中绝对路径全量替换。
