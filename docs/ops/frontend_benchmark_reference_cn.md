# 前端参考产品收敛（实验室安全小助手）

## 1. 文档目的
- 本文用于收敛“实验室安全小助手”后续前端优化可参考的同类产品界面模式。
- 目标不是照搬某个产品，而是提炼适合当前项目阶段的：
  1. 展示优先的信息架构
  2. 低学习成本的操作路径
  3. 可讲解、可演示、可继续演进的页面组织方式
- 当前项目定位仍以“课程 / 大创展示优先”为主，因此本参考优先服务：
  - 首次进入不迷路
  - 演示主线更聚焦
  - 教师 / 评委一眼看懂系统分层
  - 后续小步迭代而不是大重构

## 2. 当前页面现状（作为参照起点）
- 当前 `web_demo` 已从单页堆叠收敛为“左侧导航 + 主内容分区”。
- 当前默认展示主线已冻结为：
  1. 平台总览
  2. 智能问答（lab lane）
  3. 准入阻断
  4. 培训与看板
  5. 指标收口
- 当前仍可继续提升的前端感受主要集中在：
  - 页面层级是否更清楚
  - 不同角色（老师 / 学生 / 管理者）能否快速理解各页价值
  - 次要页面是否能降低表单压迫感
  - 页面是否更像“可交付产品”而不是“功能集合页”

## 3. 参考产品与可借鉴模式

### 3.1 SafetyCulture：移动友好、任务驱动、把“问题上报”做轻
**参考点**
- SafetyCulture 的培训指南显示，它把首页、Inspections、Actions、Issues、Training、Assets 拆成明确入口，减少用户在一个页面里同时面对过多功能。
- 问题上报页强调“最少必填字段先完成，再补更多信息”，并允许附加图片、视频、站点和通知对象。
- 动作与问题都围绕“状态、优先级、负责人、地点”组织，便于讲清“发现问题 -> 跟进处理 -> 可追踪”。

**对本项目的借鉴**
- “事故复盘”与“准入阻断”都适合借鉴这种“核心字段先填、补充字段后放”的轻表单方式。
- 培训与看板页可以继续强化“培训动作”和“管理结果”两层，不要把配置、统计、洞察完全混在一起。
- 对展示型项目来说，SafetyCulture 的价值不在视觉花哨，而在于：
  - 首页入口清楚
  - 一屏只讲一种动作
  - 行动项天然带状态

**不建议直接照搬的部分**
- SafetyCulture 偏真实生产工具，字段和流程非常细。当前项目如果照搬过多字段，会让答辩展示显得过重。

### 3.2 EcoOnline：管理端看板强调“实时可见 + KPI + 趋势”
**参考点**
- EcoOnline 官方页面强调 incident management 的几个核心界面价值：
  - reporting 简单
  - real-time dashboards
  - customizable analytics
  - 组织级可见性
- 这类产品普遍会把管理层最关心的信息放在上半屏：
  - KPI 卡片
  - 趋势图
  - 分类分布
  - 待处理事项

**对本项目的借鉴**
- “培训与看板”页应继续维持“先结论、后细节”的结构：
  1. 顶部先给关键指标
  2. 中部给风险热点 / 低置信积压 / 最近高风险场景
  3. 底部才放更细的筛选和明细
- 如果后面继续改看板，优先补：
  - 本周风险热点
  - 培训完成率 / 抽题表现
  - 低置信问题待补强数
  - 最近一次阻断类型
- 对展示来说，管理页最怕“有很多模块但没有一句结论”。因此每个看板区块最好都能一句话解释“这块告诉你什么”。

**不建议直接照搬的部分**
- 目前项目演示更偏“闭环能力展示”，不是成熟 BI 平台，不适合直接引入很多复杂筛选器和大图表布局。

### 3.3 Dify：把“知识库 / 工作流 / 应用”边界说清楚
**参考点**
- Dify 文档强调：知识库不是孤立存在，而是为具体应用提供外部知识来源。
- 它把“知识库配置”“检索策略”“关联应用”等能力放在相对清楚的边界中，而不是混进聊天页面里。
- 在知识检索上，Dify 明确区分关键词、语义、重排序等配置，帮助用户理解“为什么会命中这条内容”。

**对本项目的借鉴**
- 当前“本地 Dify / 知识库”工作区方向是对的，应继续保持独立，不要重新塞回问答页。
- 后续如果继续优化该页，建议优先突出：
  1. 当前知识库是否可用
  2. 当前问答是否走正式知识库工作流
  3. 当前问题命中了哪些知识
  4. 哪些问题属于低置信待补强
- 换句话说，这一页的目标不是“参数很多”，而是“让老师看懂：这不是普通聊天，而是有知识底座和命中证据的问答”。

**不建议直接照搬的部分**
- Dify 更偏平台控制台；本项目是展示型应用，不适合把模型参数、检索参数、流程节点全部暴露在默认前台。

### 3.4 incident.io / FireHydrant 一类事故产品：时间线和后续动作要清楚
**参考点**
- incident.io 的 post-incident timeline 强调：
  - 左侧事件流 / 活动流
  - 可以补充自定义事件
  - 时间线不是单纯文本，而是“按发生顺序讲清楚发生了什么”
- 这类产品的复盘页通常不会一上来堆很多长文本框，而是先让用户抓住：
  1. 事件是什么
  2. 何时发生
  3. 影响范围
  4. 关键处置动作
  5. 后续改进项

**对本项目的借鉴**
- “事故复盘”页下一轮最值得做的，不是加更多字段，而是：
  - 强化时间顺序
  - 先填核心摘要
  - 再补原因分析和改进措施
- 如果保持当前轻量前端路线，推荐采用：
  - 核心信息卡
  - 时间线卡
  - 原因与改进卡
  这样的三段式，而不是长表单一次铺开。

**不建议直接照搬的部分**
- 这类产品通常围绕真实值班流、告警流和协同工具集成设计，项目当前没有必要模拟完整 incident command center。

### 3.5 Linear / Notion：侧边栏组织与默认视图值得借鉴
**参考点**
- Notion 强调 sidebar 对知识空间的组织作用：用户可以很快知道“哪里是常用入口，哪里是信息归档”。
- Linear 强调默认视图、Inbox / Triage、列表与看板切换，帮助用户先做优先处理，再展开细节。
- 两者共同点不是“长得现代”，而是：
  - 导航层级清楚
  - 默认首页有意义
  - 视图切换成本低
  - 用户总能知道当前在哪个工作场景

**对本项目的借鉴**
- 当前已经有左侧导航，这是对的；下一步更值得继续强化的是：
  1. 每个入口的角色定位更明显
  2. 默认首页继续承担“导览和讲解提词器”作用
  3. 次级页面减少无关信息干扰
- 比如：
  - 总览页面向“第一次看系统的人”
  - 智能问答页面向“验证知识问答能力”
  - 准入阻断页面向“展示规则约束能力”
  - 培训与看板页面向“展示管理闭环”
  - 事故复盘页面向“追问扩展”

**不建议直接照搬的部分**
- 当前仓库仍是轻量模板页面，不适合为了模仿 Linear / Notion 而引入复杂路由、快捷键系统或大量工作台元件。

### 3.6 Intercom / 企业知识助手：AI 问答页面要证明“有依据”
**参考点**
- Intercom Fin 的核心口径不是“模型会聊天”，而是“用已有帮助中心知识来回答，并随知识更新而更新”。
- 这一类产品会持续强调：
  - 回答基于知识源
  - 回答边界清楚
  - 错误时有兜底或人工补位

**对本项目的借鉴**
- 智能问答页应继续保持“知识链路说明 + 当前 lane 标识 + 来源可解释性”的表达。
- 对答辩展示来说，最重要的是让评委明白：
  - 这不是自由聊天
  - 这是实验室安全知识问答
  - 回答背后有正式知识库工作流和可追踪命中

## 4. 可提炼出的前端设计原则（适合当前项目）

### 原则 1：默认首页先讲清系统，不先压用户做操作
- 总览页要承担“导览 + 场景解释 + 演示入口”的职责。
- 第一屏最好回答三个问题：
  1. 这是做什么的
  2. 当前推荐先看什么
  3. 这个系统和普通聊天有什么不同

### 原则 2：每个页面只承载一个核心任务
- 问答页：证明“能答”
- 准入阻断页：证明“能拦”
- 培训与看板页：证明“能管”
- 事故复盘页：证明“能追溯”
- 本地 Dify / 知识库页：证明“有知识底座”

### 原则 3：先结论、后明细、再配置
- 对展示型页面，首屏先给一句结论和关键数据。
- 明细与配置不要抢首屏注意力。
- 这尤其适用于培训与看板页、知识库页、事故复盘页。

### 原则 4：核心字段前置，补充字段后置
- 特别适合：
  - 准入清单提交
  - 事故复盘
  - 风险场景创建
- 可以减少“页面很重、看起来难用”的第一印象。

### 原则 5：所有 AI 页都要解释当前链路
- 至少要清楚提示：
  - 当前是 lab 还是 agent
  - 是否命中正式知识库
  - 当前结果更像正式回答还是兜底模式
- 这是本项目区别于普通聊天页的关键展示点。

### 原则 6：管理页要像“看板”，不是“表单集合”
- 培训与看板页应优先呈现：
  - 指标
  - 洞察
  - 异常
  - 待行动项
- 少把大量输入控件直接堆在首屏。

## 5. 对当前项目最适合的下一步前端优化顺序

### P1：事故复盘页表单减压
建议优先级最高。
- 原因：
  - 当前它最容易显得“信息太密”
  - 又是老师追问时可能会打开的扩展页
  - 改动风险低，不影响主线
- 建议动作：
  1. 改成“核心信息 / 时间线 / 原因与改进”三段式
  2. 补充字段折叠或弱化
  3. 降低首屏 textarea 堆叠感

### P2：培训与看板页补一句话结论层
- 目前层级已经比之前清楚，但还可以进一步增强“管理者一眼看懂”的感觉。
- 建议给每个洞察区块补一句解释文案，例如：
  - 这组数据说明当前最需要补强哪些问题
  - 这组数据说明最近哪类场景最危险

### P3：知识库页补“命中解释”与“待补强提示”
- 重点不是增加参数，而是增加可解释性。
- 建议让用户更容易看懂：
  - 为什么当前问题命中了这几条知识
  - 哪些问题仍然可能答得不稳

### P4：总览页补“角色化入口说明”
- 可以在不改结构的前提下，继续强化：
  - 老师看什么
  - 学生演示什么
  - 管理者关注什么

## 6. 当前不建议做的事
- 不建议现在引入 React / Next.js 重构，只为了看起来更像成熟 SaaS。
- 不建议现在做很多高级图表与复杂筛选，容易把展示主线拖重。
- 不建议把 Dify 的底层配置参数大量暴露到展示前台。
- 不建议为了“看起来功能很多”再往首页塞更多模块。
- 不建议同时大改多个页面；应继续按“一页一轮”的节奏优化。

## 7. 推荐的后续执行口径
- 当前可采用的收敛口径：
  - 先参考同类产品的信息架构与页面分工，不照搬视觉风格；
  - 优先优化“事故复盘页表单减压”，其次补强“看板解释层”和“知识命中解释层”；
  - 保持现有轻量模板结构，继续以小步、低风险、可演示为原则推进。
