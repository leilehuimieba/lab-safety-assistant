# 申报书差距整改计划

> 形成日期：2026-04-21  
> 适用项目：实验室安全小助手  
> 用途：围绕申报书差距对照结果，形成后续可执行、可分工、可汇报的整改计划。

---

## 1. 整改目标

将当前“可运行、可展示、可答辩”的项目状态，逐步推进到更接近申报书完整验收要求的状态，重点补齐以下 6 类问题：

1. **知识库规模不足**：`398 -> 1200 -> 3000+`
2. **性能指标不达标**：尤其是 `P95` 响应时延明显偏高
3. **试点应用证据缺失**：缺不少于 2 个实验室场景试点
4. **用户侧量化指标缺失**：缺有效用户统计与满意度数据
5. **角色权限证据不足**：缺学生/实验人员/管理员分权限材料
6. **成果材料未成套**：缺正式需求、设计、测试、运维、用户手册、总结等文档

---

## 2. 整改总原则

1. **先补硬指标，再补包装材料**  
   优先补知识库规模、性能、试点和用户数据。

2. **先拿到阶段过线，再冲最终目标**  
   先达到阶段性可汇报状态，再向完整结题标准推进。

3. **尽量复用现有文档和证据**  
   当前仓库已有大量素材，重点是按申报书口径重新组织，而不是全部重写。

4. **优先补“老师一眼能看懂”的证据**  
   比如知识库条目数、试点场景、用户满意度、角色权限矩阵、正式成果包。

## 4. 分阶段推进建议

### 第一阶段：补“阶段过线”最小闭环

**时间：2026-04-22 ~ 2026-05-20**

#### 目标

将项目从“可演示”推进到“能支撑阶段检查”。

#### 本阶段重点

1. 知识库先补到 `>=1200` 条
2. 角色权限矩阵与三类角色验证补齐
3. 检索评测口径建立
4. 需求说明书、技术设计说明书、测试评估报告成稿
5. 低置信度转人工机制补证

#### 阶段验收标准

1. 有一版正式阶段材料包
2. 有一版“申报书差距整改已启动”的证据清单
3. 能清楚说明当前项目不是“只有 demo”，而是在按课题推进

### 第二阶段：补“试点与性能”

**时间：2026-05-21 ~ 2026-07-15**

#### 目标

补齐申报书中最关键的“落地应用”证据。

#### 本阶段重点

1. 落地 2 个实验室场景试点
2. 启动用户数据和满意度采集
3. 完成性能专项优化第一轮
4. 建立可用性统计
5. 形成试点过程记录

#### 阶段验收标准

1. 2 个试点场景有真实记录
2. 用户开始产生可统计数据
3. 性能有明确优化前后对比

### 第三阶段：补“最终验收包”

**时间：2026-07-16 ~ 2026-09-15**

#### 目标

将项目推进到接近完整结题/验收状态。

#### 本阶段重点

1. 知识库扩到 `3000+`
2. 输出《试点应用效果报告》
3. 输出《项目总结报告》
4. 准备软著/论文材料
5. 汇总完整结题档案

#### 阶段验收标准

1. 形成正式成果包
2. 形成可答辩、可验收、可归档的一套材料

## 6. 建议近期立刻启动的 5 项动作

### 6.1 召开一次整改计划对齐会

目标：不是停留在文档层面，而是明确“谁负责什么、什么时候交什么”。

### 6.2 优先冲知识库到 1200 条

理由：这是最直观的阶段性硬指标。

### 6.3 补角色权限矩阵与截图证据

理由：开发量未必最大，但对“项目完整度”提升很明显。

### 6.4 启动检索与性能专项报告骨架

理由：老师追问“指标怎么证明”时，需要快速拿出可读报告。

### 6.5 尽快确定 2 个试点场景

理由：没有试点，就难以补齐后续用户数、满意度、可用性和效果报告。
