# 实验室安全小助手部署与运维手册

> 文档版本：v1.0  
> 形成日期：2026-04-21  
> 对应项目：实验室安全小助手（Lab Safety Assistant）  
> 当前基线：`v8.2`  
> 适用阶段：课程 / 大创展示优先阶段  
> 文档定位：作为当前项目正式部署与运维手册，用于说明系统在当前阶段的启动方式、环境准备、巡检方法、常见问题处理和展示保障要求。  

---

## 1. 文档目的

本手册用于统一“实验室安全小助手”当前阶段的部署与运维口径，重点服务以下任务：

1. 本地演示环境启动与停止；
2. 本地接服务器 Dify 的桥接式运行；
3. 展示前技术预检与现场保障；
4. 常见运行问题排查；
5. 申报材料、试点准备和课程答辩中的运行说明归档。

本手册强调以下原则：

1. 以当前仓库内已有脚本和文档为准；
2. 优先采用**最短、最稳、最可复现**的运行路径；
3. 以演示可用、试点可用为首要目标；
4. 不把正式生产级长期运维要求误写成当前已完成状态。

## 2. 当前阶段部署与运维定位

### 2.1 当前定位

当前项目的部署与运维工作，主要服务于：

1. 课程展示；
2. 项目答辩；
3. 小范围试点；
4. 阶段性功能验证；
5. 申报材料支撑。

### 2.2 当前不是首要目标的内容

以下内容当前不是本项目部署与运维的首要目标：

1. 面向全校正式上线的高可用运维体系；
2. 完整生产级监控、告警、自动伸缩；
3. 多环境自动化发布平台；
4. 长周期正式值守与 SLA 体系；
5. 大规模账号与权限平台集成。

### 2.3 当前推荐口径

在答辩、试点或申报材料中，建议统一这样表述：

1. 当前系统已形成 `v8.2` 演示基线；
2. 当前可通过统一脚本在本地稳定启动 `web_demo`；
3. 实验室安全问答正式链路基于 Dify 工作流设计；
4. 当前保留结构化 fallback 作为上游异常时的兜底；
5. 当前主要剩余问题是**延迟波动**，不是系统完全不可运行。

## 3. 部署模式总览

当前项目建议使用以下三种运行方式，根据实际场景选择。

### 3.1 模式 A：本地演示模式（推荐默认）

适用场景：

1. 本地开发；
2. 课程展示前自测；
3. 试点前功能确认；
4. 无需依赖远端公网访问的本机演示。

特点：

1. 入口清晰；
2. 启停脚本已提供；
3. 默认端口固定；
4. 最适合当前阶段做稳定复现。

默认地址：

- `http://127.0.0.1:8088`

### 3.2 模式 B：本地接服务器 Dify 桥接模式

适用场景：

1. 本机可运行前端演示服务；
2. 本机未完整部署 Dify；
3. 服务器已有可用 Dify 环境；
4. 希望维持“本地页面 + 远端 Dify 后端”的运行方式。

特点：

1. 本地依然可以直接打开演示页面；
2. Dify 后端由服务器提供；
3. 对当前展示和提交阶段较实用；
4. 应明确说明这不是“完全单机部署”。

默认地址：

- `http://127.0.0.1:8090`

### 3.3 模式 C：服务器在线演示模式

适用场景：

1. 需要远程访问；
2. 需要在服务器上集中部署演示版本；
3. 需要对外临时展示演示链接。

特点：

1. 适合集中部署；
2. 可结合反向代理或临时隧道；
3. 更接近线上演示形态；
4. 当前仍以“演示优先”而非正式生产运维为定位。

## 5. 环境准备

### 5.1 基础依赖

在 Windows 本地运行前，建议先确保已具备：

1. Python 可用；
2. PowerShell 可执行脚本；
3. 项目依赖已安装；
4. 仓库代码路径完整可读写。

参考安装方式：

```powershell
pip install -r scripts/requirements-web-ingest.txt
pip install fastapi uvicorn pyyaml requests pydantic
```

### 5.2 环境变量文件

本地演示依赖以下文件：

- `.env.web_demo`

若该文件缺失，可由模板复制：

```powershell
Copy-Item .env.web_demo.example .env.web_demo
```

### 5.3 当前最少配置要求

`.env.web_demo` 中至少建议配置以下之一：

1. `DIFY_APP_API_KEY`
2. `OPENAI_API_KEY`

说明：

1. 若 `DIFY_APP_API_KEY` 和 `OPENAI_API_KEY` 都为空，脚本会警告，系统能力会明显受限；
2. 若没有 Dify，但配置了 `OPENAI_API_KEY`，系统仍可在结构化 fallback 口径下跑通本地演示；
3. 若希望使用正式实验室安全问答链路，应补齐 Dify 相关配置。

### 5.4 关键配置项说明

当前常见配置项包括：

1. `DIFY_BASE_URL`
2. `DIFY_APP_API_KEY`
3. `DIFY_TIMEOUT`
4. `OPENAI_BASE_URL`
5. `OPENAI_API_KEY`
6. `OPENAI_MODEL`
7. `OPENAI_FALLBACK_MODELS`
8. `OPENAI_TIMEOUT`
9. `DEMO_PORT`

### 5.5 配置使用注意事项

1. 不在公开材料中直接暴露真实密钥；
2. 不将私钥、token 或敏感配置提交到公开仓库；
3. 演示口径中可说明“已配置”，但不要在答辩现场展示完整 key；
4. 修改 `.env.web_demo` 后，建议重新启动服务以确保配置生效。

## 7. 本地接服务器 Dify 桥接模式部署步骤

### 7.1 适用说明

当本机尚未完整部署 Dify，但服务器已有可用环境时，建议使用该方式作为当前阶段的最短落地方案。

### 7.2 启动命令

在仓库根目录执行：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/run_local_demo_via_server_dify.ps1
```

如需显式指定端口，可使用：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/run_local_demo_via_server_dify.ps1 `
  -TunnelPort 18080 `
  -DemoPort 8090
```

### 7.3 当前默认桥接参数

根据现有项目文档，当前常见桥接参数包括：

1. 远端 Dify：`127.0.0.1:8080`
2. 本地 tunnel 端口：`18080`
3. 本地 demo 端口：`8090`

### 7.4 最小验证步骤

建议至少做以下三步验证：

#### Step 1：检查 health

```powershell
Invoke-WebRequest -UseBasicParsing http://127.0.0.1:8090/health
```

#### Step 2：检查 meta

```powershell
Invoke-RestMethod http://127.0.0.1:8090/api/meta
```

#### Step 3：检查聊天接口

```powershell
$body = @{ question = '危险实验开始前最关键的阻断项是什么？'; mode = 'lab' } | ConvertTo-Json
Invoke-RestMethod `
  -Uri http://127.0.0.1:8090/api/chat `
  -Method Post `
  -ContentType 'application/json' `
  -Body $body `
  -TimeoutSec 180
```

### 7.5 停止桥接运行

```powershell
powershell -ExecutionPolicy Bypass -File scripts/stop_local_demo_via_server_dify.ps1
```

### 7.6 口径注意事项

使用该模式时，建议统一说明：

1. 本地页面运行在本机；
2. Dify 后端来自已配置的服务器环境；
3. 这是当前阶段可接受的演示与验证方案；
4. 该模式不应表述成“已完成纯本机完整 Dify 单机部署”。

## 10. 启动后标准巡检流程

### 10.1 最小巡检目标

每次运行成功后，至少完成以下巡检：

1. 服务是否启动；
2. 端口是否可访问；
3. 健康检查是否正常；
4. 页面核心模块是否可见；
5. 问答、阻断、看板主链路是否基本可用。

### 10.2 巡检步骤

#### 步骤一：检查 health

访问：

- `http://127.0.0.1:8088/health`

或桥接模式：

- `http://127.0.0.1:8090/health`

预期：

- 返回 `200`
- body 中含 `status=ok` 或等价正常信息

#### 步骤二：检查 meta

访问：

- `http://127.0.0.1:8088/api/meta`

重点关注：

1. `app_version`
2. `acceptance_status`
3. `chat_lane_lab`
4. `knowledge_base_imported`
5. `formal_eval_score`
6. `stability_status`

#### 步骤三：检查页面主模块

进入页面后，确认至少能看到：

1. 平台总览
2. 智能问答
3. 准入阻断
4. 培训与看板

#### 步骤四：做一轮固定问题验证

推荐固定问题：

- `危险实验开始前最关键的阻断项是什么？`

重点不在于现场深度扩题，而在于确认：

1. 页面能返回回答；
2. 页面可继续进入阻断页面；
3. 系统口径与当前答辩材料一致。

#### 步骤五：做一轮阻断验证

建议故意不满足一个关键项，确认系统是否能给出：

- `清单阻断，暂不可开工`

#### 步骤六：看一眼管理端看板

确认至少能看到：

1. 清单阻断率
2. 培训通过率
3. 低置信问题
4. 最近高风险场景

## 11. 展示前预检与现场保障

### 11.1 展示前建议检查项

在答辩、课堂展示或试点演示前，建议至少检查以下内容：

1. 页面入口可打开；
2. 左侧主模块齐全；
3. 固定问题可运行；
4. 阻断模块可正常给出阻断结果；
5. 日志中无明显连续报错；
6. 当前统一指标口径准备完毕。

### 11.2 当前统一收口指标

建议现场统一使用以下收口指标：

- 知识库正式导入：`398`
- 正式回归：`20/20`
- 稳定性验证：`3/3 PASS`
- 当前主要待优化问题：**延迟波动，不是正确率问题**

### 11.3 现场运行建议

1. 不临时更换主线；
2. 不现场改配置；
3. 不现场排大问题；
4. 不同时打开大量不必要页面；
5. 优先使用已验证固定问题和固定展示顺序。

### 11.4 响应偏慢时的处理建议

若现场问答等待偏长，建议：

1. 不连续重复点击；
2. 不临时更换题目；
3. 直接切入准入阻断页面说明门禁价值；
4. 最终回到统一指标口径收尾。

## 13. 常见问题与排查建议

### 13.1 启动脚本提示缺少环境文件

可能原因：

1. `.env.web_demo` 不存在；
2. 模板未复制；
3. 仓库路径错误。

处理建议：

1. 先确认当前目录正确；
2. 执行模板复制；
3. 补齐最小配置后重新启动。

### 13.2 启动失败，提示端口被占用

可能原因：

1. `8088` 已被其他进程占用；
2. 上一次服务未正常退出；
3. 本地已有其他 demo 在运行。

处理建议：

1. 先执行停止脚本；
2. 查看占用进程；
3. 必要时修改 `DEMO_PORT`；
4. 若使用桥接模式，建议继续让桥接模式走 `8090`，避免与 `8088` 冲突。

### 13.3 health 不通或页面打不开

可能原因：

1. 服务未成功启动；
2. 启动后立即退出；
3. Python 或依赖缺失；
4. 配置项存在问题。

处理建议：

1. 先看 `runtime.json` 是否生成；
2. 再看日志和错误日志；
3. 确认依赖已安装；
4. 重新启动并观察控制台提示。

### 13.4 问答返回 fallback 或与预期链路不一致

可能原因：

1. 当前环境未配置 Dify；
2. Dify 上游不可用；
3. 当前环境处于结构化回退模式；
4. 桥接成功但远端工作流本身状态不稳定。

处理建议：

1. 先通过 `api/meta` 看当前 `chat_lane_lab`；
2. 明确区分“环境已桥接”和“正式链路完全稳定”这两件事；
3. 对外口径应以当前实际环境为准，不夸大为所有环境都已完全一致。

### 13.5 日志没有明显错误，但响应很慢

当前判断：

1. 这更接近现阶段已知问题——延迟波动；
2. 不宜简单判断为“系统不可用”；
3. 应优先采用固定问题和固定主线减少现场不确定性。

### 13.6 服务器能跑，本地不能跑

可能原因：

1. 本地未配置必要 key；
2. 本地依赖未装全；
3. 本地端口冲突；
4. 本地路径或环境变量不一致。

处理建议：

1. 优先保证本地默认脚本能启动；
2. 若时间紧张，可临时采用桥接模式；
3. 说明本地与服务器环境差异，不要混淆成同一结论。
