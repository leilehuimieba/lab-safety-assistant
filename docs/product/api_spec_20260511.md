# 实验安全前置哨 — API 规范补充稿（2026-05-11）

> 目标：统一当前前后端接口口径，方便答辩、联调和后续测试。

## 1. 通用约定

### 1.1 风格

- 采用 REST 风格
- 请求与响应均为 JSON
- 前缀统一为 `/api`
- 兼容历史链路保留别名，不影响主线

### 1.2 响应约定

#### 成功

```json
{
  "data": {}
}
```

当前项目部分接口直接返回业务对象，不强制包一层 `data`；后续若统一版本化，可逐步收敛。

#### 失败

```json
{
  "detail": "error message"
}
```

### 1.3 错误码建议

| HTTP 状态 | 含义 |
|---|---|
| 200 | 成功 |
| 400 | 参数错误 |
| 404 | 资源不存在 |
| 500 | 服务内部错误 |
| 502 | 上游服务失败 |

## 3. 核心接口详情

### 3.1 `POST /api/chat`

#### 请求

```json
{
  "mode": "lab",
  "question": "锂电池拆解前需要注意什么？"
}
```

#### 返回字段

| 字段 | 说明 |
|---|---|
| answer | 答案正文 |
| mode | lab / agent |
| model | 实际模型或规则引擎标识 |
| decision | llm_answer / rule_blocked / emergency_redirect / need_more_info / llm_low_confidence / llm_fallback_structured |
| risk_level | 风险等级 |
| matched_rule_id | 命中的规则 ID |
| matched_rule_action | 规则动作 |
| low_confidence | 是否低置信 |
| low_confidence_reason | 原因 |
| followup_logged | 是否写入低置信队列 |
| citations | 来源引用列表 |

### 3.2 `POST /api/risk/assess`

#### 请求

```json
{
  "scenario": "锂电池拆解，使用金属工具，未穿绝缘手套。"
}
```

#### 返回重点

- `risk_score`
- `risk_level`
- `key_hazards`
- `ppe`
- `forbidden`
- `emergency_actions`
- `recommended_steps`
- `citations`

### 3.3 `POST /api/checklist/template`

#### 请求

```json
{
  "scenario": "......",
  "chemicals": "",
  "equipment": "",
  "procedure": ""
}
```

#### 返回重点

- `risk_score`
- `risk_level`
- `key_hazards`
- `checklist`
- `recommended_actions`
- `citations`

### 3.4 `POST /api/checklist/submit`

#### 请求

```json
{
  "scenario": "......",
  "operator": "张三",
  "checklist": [
    {
      "id": "sop_reviewed",
      "label": "SOP, SDS, and experiment objective have been reviewed.",
      "critical": true,
      "checked": false,
      "note": ""
    }
  ]
}
```

#### 返回重点

- `record_id`
- `allow_start`
- `blocking_reasons`
- `next_actions`
- `review_status`

### 3.5 `PATCH /api/checklist/{record_id}/review`

#### 请求

```json
{
  "reviewer": "李老师",
  "action": "reject",
  "comment": "先完成双人核对。"
}
```

#### 返回重点

- `review_status`
- `reviewed_by`
- `reviewed_at`
- `review_comment`

## 4. 接口设计中的竞争力点

### 4.1 统一的判断链路

现在的接口不是零散功能，而是同一条链路：

`安全问答 -> 风险评估 -> 清单生成 -> 提交阻断 -> 老师审核 -> 看板统计`

这比“单纯问答接口”更有竞争力。

### 4.2 兼容历史链路

保留以下别名：

- `/api/risk_assess`
- `/api/admin/export`
- `/api/admin/weekly-report`
- `/api/training/roster`

这样既不破坏历史演示，也不影响当前主线。

### 4.3 适合答辩的接口特征

1. 字段明确；
2. 返回结构化；
3. 阻断可解释；
4. 审核可追踪；
5. 看板可统计。
