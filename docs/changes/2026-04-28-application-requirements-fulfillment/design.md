# Design

## 目标概述
- 将申报书中的研究目标、功能模块、指标要求和结题成果转为当前仓库可执行的需求规格、差距矩阵和任务清单。

## 方案概要
- 一句话方案：不直接大改代码，先建立“申报书兑现层”的统一需求和验收口径，再按 P0/P1/P2 推进实现。
- 主流程：
  1. 解码并读取申报书正文。
  2. 提取四大模块、阶段目标、最终目标、关键指标、研究方法和资源约束。
  3. 对照当前仓库已有能力。
  4. 生成需求规格说明和差距矩阵。
  5. 创建 change 工作区并设为当前主推进项。
  6. 后续从 1000 条核心知识库和评测指标开始补齐。

## 关键决策
- 决策 1：以申报书目标作为后续结题验收目标，以 `v8.2` 作为当前可用原型基础。
- 决策 2：申报书中的绝对化表述在内部拆成“阶段目标”和“挑战目标”，不在无证据时对外宣称已达成。
- 决策 3：先补数据规模、指标和真实试运行证据，不优先做大 UI 改版。
- 决策 4：LoRA / 联邦架构 / 多端正式上线作为增强项，不阻塞 2026-06-30 前的核心结题交付。

## 影响模块

- 文档：旧申报书差距矩阵（已删除，申报书主线暂停；必要时从 Git 历史恢复）
- change：`docs/changes/2026-04-28-application-requirements-fulfillment/`
- 索引：`docs/changes/INDEX.md`、`docs/changes/active.txt`
- 路线：`docs/roadmap.md`、`docs/README.md`

## 对展示主线的影响
- 对演示链路：不破坏现有 `v8.2` 演示链路。
- 对门禁 / 验证：后续需要新增申报书指标 gate，包括知识库规模、专业准确率、安全拒答、响应时延、动态更新、试运行反馈。
- 对答辩材料：后续答辩/结题口径从“演示可复现”升级为“申报书承诺兑现进度可说明”。

## 风险与取舍
- 风险：申报书目标大于当前演示原型，若一次性改代码会失控。
- 取舍原因：先建规格和差距矩阵，确保每个后续实现都服务申报书承诺。

## 未决问题
- 3000 条知识库的真实来源和版权/授权边界需要人工确认。
- 有效回答率和专业准确率是否由实验室安全老师人工审核，需要确定审核人和题集。
- 试运行是否能满足“3 个月”原始表述；若时间不足，应在结题材料中说明采用阶段性试运行。

## 不做项
- 本次不新增业务功能代码。
- 本次不删除原演示冻结 change。
- 本次不伪造真实试点反馈或知识库规模。
