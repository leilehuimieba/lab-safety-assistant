# 实验安全前置哨 — 实现与测试计划补充稿（2026-05-11）

> 目标：把“能跑”提升为“更稳定、更像产品、更能打答辩”。

## 1. 实现阶段建议

### 1.1 环境搭建

#### 推荐固定环境

| 项目 | 建议 |
|---|---|
| Python | `.venv312` |
| Node | 项目内 `web_demo/frontend` 的本地 npm/pnpm 环境 |
| 后端启动 | `python -m uvicorn web_demo.app:app --host 127.0.0.1 --port 8088` |
| 前端构建 | `npm run build` |
| Embedding | 默认 `ENABLE_EMBEDDING=0`，演示更稳 |

#### 建议保留的环境变量

- `ENABLE_EMBEDDING`
- `OPENAI_BASE_URL`
- `OPENAI_API_KEY`
- `OPENAI_MODEL`
- `DIFY_APP_API_KEY`
- `DIFY_BASE_URL`
- `DIFY_TIMEOUT`

### 1.2 编码规范

#### Python

- 路由层只负责收参和回参
- service 层处理业务逻辑
- repositories 只做文件读取/缓存/常量
- 单一函数职责明确，不把所有逻辑塞进一个方法

#### TypeScript

- 所有 API 都走 `src/api/client.ts`
- 页面组件只负责渲染和交互
- 类型定义与后端模型保持一致
- 不用字符串魔法值乱传字段

### 1.3 模块开发顺序

建议按下面顺序推进：

1. **问答**
2. **风险评估**
3. **开工清单**
4. **老师审核**
5. **管理看板**
6. **培训 / 事故 / 系统状态**

这样最容易保证主线不跑偏。

### 1.4 版本控制

建议：

- 主分支只保留可演示版本
- 每次修改都要有构建验证
- 文档和代码同步提交
- 关键修复单独留 commit message

### 1.5 代码审查重点

#### 前端

- 事件是否重复触发
- 路由是否能切换
- 空值是否会报错
- 页面是否一屏讲清楚

#### 后端

- 导入是否完整
- 接口字段是否对齐
- 错误是否有明确 detail
- 文件写入是否能落盘

## 2. 测试阶段建议

### 2.1 测试策略

采用“四层测试”：

1. 单元测试
2. 集成测试
3. 系统测试
4. 用户验收测试

### 2.2 测试矩阵

| 测试类型 | 重点对象 | 目标 |
|---|---|---|
| 单元测试 | 风险评估、规则匹配、低置信判断、看板统计 | 确保核心逻辑正确 |
| 集成测试 | API 路由、文件持久化、前后端字段对齐 | 确保模块能拼起来 |
| 系统测试 | 首页、清单、老师工作台、看板、系统状态 | 确保演示闭环可用 |
| 性能测试 | 首屏加载、风险评估、看板加载 | 确保答辩现场不卡 |
| 安全测试 | 输入校验、危险问题硬阻断、异常兜底 | 确保不输出危险指导 |
| UAT | 学生/老师/管理员三角色流程 | 确保真的能讲、能用 |

### 2.3 当前最关键的自动化 Gate

- `npm run build`
- `python -m pytest -q`
- `GET /health`
- `GET /api/meta`
- `GET /api/workspace/status`
- `POST /api/risk/assess`
- `POST /api/checklist/submit`
- `GET /api/admin/dashboard`

### 2.4 推荐测试场景

#### 高风险场景

- 锂电池拆解
- 有机溶剂明火加热
- 电气实验带电操作
- 化学品飞溅场景

#### 低风险场景

- pH 试纸测试
- 常规观察类实验

#### 低置信场景

- 新型材料
- 冷门仪器
- 非知识库覆盖的边界问题

### 2.5 测试输出物

建议至少保留以下证据：

1. 构建日志
2. pytest 结果
3. 关键 API 响应
4. 浏览器截图
5. 看板截图
6. 错误修复记录

## 3. 当前项目的竞争力优化建议

### 3.1 P0：必须做

1. **主线统一**
   - 所有页面统一围绕“实验前能不能开工”讲故事。

2. **数据可见**
   - 看板必须展示阻断率、低置信、培训、风险热点。

3. **流程闭环**
   - 问答、评估、清单、审核、看板必须闭环。

4. **证据齐全**
   - 构建、测试、接口、截图要能拿得出手。

### 3.2 P1：建议做

1. 选 3 类典型实验场景做 demo 定制；
2. 增加更明确的老师审核建议模板；
3. 强化系统状态页，让评委看到“项目是活的”；
4. 补齐一个简洁的测试报告模板。

- SQLite 落地
- 登录/角色权限
- 事故闭环更细化

## 4. 结论

如果目标是“更有竞争力”，**当前最值得优化的是展示和证据，而不是结构复杂度**。

换句话说：

- 不要把项目做成更大的系统；
- 要把项目做成更清楚、更稳定、更能解释、更新鲜的实验前安全决策助手。
