# 大创申报书——项目定义

---

## 一、项目名称

**面向高校实验室安全的轻量级实验前安全检查助手**

（备选：Lab Safety Copilot —— 基于规则引擎与知识检索的实验前安全决策系统）

---

## 二、项目背景与研究意义

### 2.1 现实背景

高校实验室安全事故每年都有发生。据教育部实验室安全检查通报，仅 2024 年全国高校实验室安全现场检查就发现隐患数万项，其中化学品管理、用电安全、个体防护等问题占比最高。

现有管理手段集中在三个方向：

- **安全培训与考试**：学生通过线上考试证明自己学过安全知识
- **综合 EHS 管理平台**：面向管理者的台账、检查、隐患上报系统
- **AI 安全问答**：基于大语言模型的通用安全知识问答

三者共同的问题是：**它们解决了"知不知道"和"事后记没记"，但没有解决"开不开工"**。

### 2.2 核心问题

一个学生在实验室准备做实验，面临的实际问题是：

> 今天这个具体的实验（比如乙醇加热回流），在我当前的准备条件下（比如通风橱坏了、护目镜找不到了），到底能不能做？如果缺了什么，是我自己补上就行，还是必须找老师？

培训考试回答不了这个问题（考试通过 ≠ 具体场景下能正确判断）。EHS 平台回答不了这个问题（它管台账，不管即时决策）。通用 AI 问答也回答不了（它只被动回答你问的问题，不会主动追问你漏了什么，更不会给你一个阻断结论）。

### 2.3 研究意义

本项目将实验室安全检查从"事后合规"前移到"事前决策"——在学生开工之前的 1-2 分钟内，完成风险识别、清单确认、阻断判断和老师审核闭环。这不只是一个技术工具，而是一种将安全管理制度嵌入日常实验流程的轻量化方案。

---

## 三、国内外研究现状

### 3.1 国外

国外高校实验室安全管理以制度驱动为主。以美国 Stanford University EH&S、MIT EHS 为代表，建立了完善的 Chemical Hygiene Plan 制度和在线培训体系。但其核心仍是"培训 + 人工检查 + 事故报告"，学生开工前的即时安全判断仍依赖个人判断和导师监督，缺乏系统化的自动化辅助工具。

### 3.2 国内

| 方案类型 | 代表产品/系统 | 解决的问题 | 未解决的问题 |
|---|---|---|---|
| 安全培训考试 | 各高校在线考试系统 | 证明学生培训过 | 培训通过 ≠ 具体实验场景能正确判断 |
| 综合 EHS 平台 | 高校实验室安全综合管理平台 | 台账、检查、隐患、报表 | 部署重、偏管理视角、学生不使用 |
| AI 安全问答 | 通用大模型 + 安全知识库 | 被动回答安全问题 | 不主动追问、不给阻断结论、不留审核记录 |
| 老师口头/纸质管理 | 人工检查 | 直接有效 | 覆盖不全、无记录可追溯 |

### 3.3 空白点

**没有人做的是：** 把安全检查从"事后记录"变成"事前阻断"——在学生拧开试剂瓶之前，系统根据他输入的具体实验内容和当前准备条件，给出可操作的结构化判断结论，并在需要时将高风险事项推送给老师确认，形成完整决策闭环。

## 四、项目内容与目标

### 4.1 做什么

一个轻量级的实验前安全检查助手（Web 应用），核心能力：

1. **实验场景输入**：学生输入实验名称、试剂、设备、操作步骤
2. **风险自动识别**：系统根据规则引擎和知识库检索，识别关键危险点和所需 PPE
3. **检查清单生成**：根据实验场景动态生成开工前检查项（SOP 确认、SDS 确认、PPE 确认、通风/防火/应急设备确认等）
4. **阻断决策**：存在硬阻断项（如易燃溶剂未确认通风）时，输出"暂不可开工"及具体阻断原因
5. **老师审核闭环**：高风险事项自动推送老师工作台，老师可一键批准或驳回，所有决策留痕
6. **安全问答**：基于本地知识库的中英文混合语义检索 + 大模型生成，回答附带来源引用
7. **应急卡片匹配**：口语化输入事故描述，自动匹配对应的应急处理卡片
8. **安全培训与统计**：随机抽题考核、错题归档、通过率统计
9. **管理看板**：阻断率、培训通过率、低置信问题队列、事故状态等数据可视化

### 4.2 目标

- 对 10 类以上高危实验场景实现有依据的阻断判断
- 高风险阻断正确率 ≥90%（核心测试场景）
- 学生从输入场景到获得结论，全程 ≤2 分钟
- 老师审核一个实验 ≤30 秒
- 完整决策链（自查时间、缺失项、系统结论、老师操作、时间戳）可追溯
- 系统不依赖特定商业平台（如 Dify），本地即可运行

### 4.3 不做的事（MVP 边界）

不做完整 EHS 平台、不做全校组织架构/SSO、不做全量危化品库存、不做门禁联动、不让 AI 承担最终安全许可。

## 五、创新点

### 创新一：独立规则引擎实现硬阻断——安全边界不靠 Prompt

现有 AI 安全问答的安全边界依赖 prompt 指令（"请不要回答危险问题"），但 prompt 可被绕过。本项目的规则引擎基于 YAML 配置文件独立运行，匹配到危险模式（如"金属钠遇水""易燃溶剂明火加热"）即触发硬阻断，不依赖大模型判断。规则文件可由非技术人员修改，改完即生效，无需重新训练或调参。

### 创新二：结构化决策输出——从"给一段文字"到"给一个判断"

普通 AI 问答返回一段 markdown 文本，用户看完还得自己判断"到底能不能做"。本项目的 API 返回结构化决策对象（allow_start / blocking_reasons / review_status / next_actions），前端据此渲染绿（可开工）、黄（需确认）、红（暂不可开工）三色决策卡片，管理看板可统计阻断率、阻断原因分布。

### 创新三：低置信驱动的知识演进——越用越准

当知识库检索无法覆盖用户问题时，系统不强行生成不可靠的回答，而是将其标记为低置信问题并自动入队。管理员可看到按类别和频率排序的知识盲区列表，有针对性地补充知识库。形成一个"使用→发现盲区→补充知识→更准确"的正向循环。

### 创新四：人机协同决策闭环——AI 预处理，人做最终判断

本项目的核心设计原则是"AI 不承担最终安全许可"。AI 只做风险识别、摘要生成和缺失标记，高风险实验的最终开工许可由老师确认。系统记录完整的决策证据链（学生自查时间、缺失项、系统建议、老师操作、时间戳），既保护学生也保护老师。

## 六、技术路线

### 6.1 技术架构

```
后端：Python 3.13 + FastAPI
检索：文本 token 匹配 + bge-m3 语义向量混合检索
规则：YAML 规则引擎，独立于 LLM 运行
知识库：CSV/JSON 结构化存储
模型：OpenAI-compatible API 直连（可接入本地模型或云端模型）
嵌入：Ollama 本地运行 bge-m3，支持 sentence-transformers 备选
部署：Docker 多阶段构建 + docker-compose 一键启动
测试：pytest，157 项测试全部通过
前端：待开发（Vite + TypeScript + Tailwind CSS 组件化架构）
```

### 6.2 核心数据链路

```
实验场景输入
  → 规则引擎识别硬阻断（YAML 确定性匹配）
  → 本地知识库混合检索（文本 + 语义）
  → LLM 生成风险摘要与建议
  → 规则二次校验
  → 结构化决策输出（允许 / 需老师确认 / 暂不可开工）
  → 高风险推送老师工作台
  → 老师审核（一键批准/驳回）
  → 完整决策记录归档
  → 管理看板统计
```

### 6.3 关键设计决策

- **规则引擎独立于 LLM**：安全边界是确定性的，不受模型幻觉影响
- **Dify 为可选依赖**：不将项目绑定到任何低代码平台，本地 FastAPI 即可完成核心链路
- **CSV 存储**：数据量在 5000 条以内时，CSV 文件足以支撑，无需引入数据库，降低部署复杂度

## 八、可行性分析

### 8.1 技术可行性

- 项目核心代码已完成：22 个 API 端点、6 个服务模块、157 项测试全部通过
- 核心技术栈（FastAPI、bge-m3、YAML、Docker）均为成熟开源技术，无技术风险
- 团队成员已具备 Python Web 开发、NLP、前端开发能力

### 8.2 应用可行性

- 系统不依赖特定商业平台，Docker 一键部署，单台服务器即可运行
- 不需要对接学校信息化系统（SSO/教务），单门课程即可试点
- 导师为实验室一线教师，可直接提供实验场景、真实需求和试点条件

### 8.3 风险与应对

| 风险 | 应对 |
|---|---|
| 规则覆盖不全导致误判 | 分场景逐步验证，先用 5 个高危实验验证，再扩展 |
| 知识库质量不足 | 以低置信队列驱动补充，优先覆盖试点课程涉及的知识点 |
| 真实用户接受度低 | 先让老师作为"查看工具"而非"强制审批"，降低使用门槛 |
| AI 输出不可靠 | 硬阻断走规则引擎而非 AI，综合结论强制标注依据来源 |

## 十、一句话定义

> 我们不做一个回答安全问题的 AI 聊天机器人。我们做的是一个在实验台前帮学生判断"能不能做"、帮老师快速审核、让每一次开工决策都有据可查的轻量级安全决策助手。

**三个关键词：事前（不是事后）、决策（不是信息）、闭环（不是一问一答）。**
