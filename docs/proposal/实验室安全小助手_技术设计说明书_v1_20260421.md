## 1. 文档目的

本说明书用于把“实验室安全小助手”当前已经落地的技术结构和关键实现思路收口为正式技术文档，服务于以下目标：

1. 让老师、队友和后续维护者能够快速理解当前系统是如何搭起来的；
2. 解释当前项目为什么能支撑“问答 + 风险评估 + 准入阻断 + 培训统计 + 管理看板 + 事故复盘”的闭环展示；
3. 区分“当前稳定实现”“当前展示口径”“后续优化方向”，避免把未来规划误写成已完成实现；
4. 为后续《测试与评估报告》《部署与运维手册》《项目总结报告》提供结构化输入。

## 2. 设计目标

### 2.1 总体设计目标

系统设计目标不是做一个泛化聊天机器人，而是围绕实验室安全场景，构建一个具备以下能力的闭环原型：

1. 能基于实验室安全知识库回答问题；
2. 能对高风险问题施加规则约束；
3. 能将安全建议转化为开工前检查与准入阻断；
4. 能沉淀培训、低置信问题、阻断结果与事故复盘数据；
5. 能为答辩与后续申报材料提供稳定、可复现、可解释的技术底座。

### 2.2 当前阶段设计原则

当前阶段遵循以下原则：

1. **稳定展示优先**：优先保证演示链路能跑通，而不是追求最理想的最终架构；
2. **证据优先**：优先保留可验证、可复现、可说明的链路与数据；
3. **最小闭环优先**：优先完成问答到阻断到管理的最小闭环；
4. **可扩展但不过度工程**：当前不引入超出展示必要范围的大规模抽象层。

## 3. 系统总体架构

### 3.1 架构概览

当前系统可抽象为五层：

1. **数据层**
2. **知识治理层**
3. **推理与规则层**
4. **应用服务层**
5. **验证与展示层**

用文本表示如下：

```text
数据源 -> 知识库/规则库 -> 问答/风险/阻断/培训/复盘服务 -> Web Demo -> 验证/评测/答辩材料
```

### 3.2 分层说明

#### 第一层：数据层

负责提供原始知识、规则和评测基础数据，核心文件包括：

1. `knowledge_base_curated.csv`
2. `safety_rules.yaml`
3. `eval_set_v1.csv`
4. `release_exports/v8.2/knowledge_base_import_ready.csv`
5. `web_demo/data/*.json`

#### 第二层：知识治理层

负责把网页、文档等来源加工成项目内部可复用的知识库格式，核心能力包括：

1. 网页抓取与正文清洗；
2. 文档统一入库；
3. 合并为结构兼容的知识库 CSV；
4. 供后续 Dify 或本地流程继续使用。

#### 第三层：推理与规则层

负责：

1. 知识问答；
2. 风险识别与场景分析；
3. 规则匹配与高风险约束；
4. 低置信问题记录；
5. 培训、清单、复盘等结构化业务逻辑。

#### 第四层：应用服务层

当前以 `web_demo/app.py` 为核心 FastAPI 服务入口，对外提供：

1. 页面访问入口；
2. 问答服务；
3. 风险评估与准入阻断服务；
4. 培训与统计服务；
5. 事故复盘服务；
6. 元数据与状态查询接口。

#### 第五层：验证与展示层

负责把技术实现收敛为可展示、可答辩、可复现的材料与证据，包括：

1. 正式回归结果；
2. 稳定性验证；
3. 浏览器级展示证据截图；
4. 演示脚本冻结版；
5. 答辩口径总表。

## 4. 核心组件设计

### 4.1 Web 应用服务组件

当前核心应用服务由 `web_demo/app.py` 承载，基于 FastAPI 实现。

其职责包括：

1. 提供页面入口；
2. 读取知识库、规则库和训练/复盘数据；
3. 对接外部模型或知识工作流；
4. 处理实验室安全问答、风险评估、清单阻断、培训统计和事故复盘；
5. 将部分运行结果落盘到 `artifacts/` 下的 CSV 文件中。

### 4.2 知识库组件

当前项目使用 CSV 形式维护主知识库，核心文件为：

- `knowledge_base_curated.csv`

当前设计特点：

1. 便于人工维护与审阅；
2. 便于作为 Dify 知识库导入源；
3. 便于与网页入库、统一入库脚本输出兼容；
4. 便于后续扩容和版本对比。

### 4.3 规则库组件

当前规则库使用 YAML 格式维护，核心文件为：

- `safety_rules.yaml`

规则库主要承载：

1. 全局策略；
2. 安全回答模板；
3. 关键词匹配规则；
4. 高风险问题处置动作；
5. 应急类问题的重定向响应。

### 4.4 评测组件

评测层围绕以下资产展开：

1. `eval_set_v1.csv`
2. 正式验收摘要
3. 发布汇总
4. 三轮稳定性证据

当前作用包括：

1. 验证问答链路是否可用；
2. 验证高风险拒答与应急问题处理；
3. 为答辩提供统一指标口径；
4. 为后续性能与检索优化提供基线数据。

### 4.5 展示组件

展示层以 `web_demo` 为主，辅以一套冻结后的脚本与文档：

1. `docs/ops/defense_alignment_cn.md`
2. `docs/ops/v8_2_demo_flow_freeze_cn.md`
3. `docs/ops/v8_2_demo_final_script_cn.md`
4. `docs/ops/v8_2_demo_stage_card_cn.md`

这层不直接新增业务能力，但对“把技术能力稳定讲出来”非常关键。

## 5. 数据设计

### 5.1 静态数据资产

当前静态数据资产主要包括：

| 类型 | 文件 | 作用 |
|---|---|---|
| 主知识库 | `knowledge_base_curated.csv` | 提供实验室安全知识条目 |
| 规则库 | `safety_rules.yaml` | 提供规则约束、拒答与应急模板 |
| 评测集 | `eval_set_v1.csv` | 提供问答/拒答/应急等回归测试样本 |
| 发布包 | `release_exports/v8.2/knowledge_base_import_ready.csv` | 供正式导入知识库使用 |
| 应急卡片 | `web_demo/data/emergency_cards.json` | 支撑应急相关内容 |
| 培训题库 | `web_demo/data/training_question_bank.json` | 支撑培训答题与统计 |

### 5.2 运行时记录数据

当前系统将部分运行结果写入 `artifacts/` 下的 CSV 文件，形成轻量级运行记录体系：

| 文件 | 作用 |
|---|---|
| `artifacts/low_confidence_followups/data_gap_queue.csv` | 记录低置信问题 |
| `artifacts/checklists/checklist_runs.csv` | 记录清单运行与阻断结果 |
| `artifacts/training/training_attempts.csv` | 记录培训作答结果 |
| `artifacts/training/training_mistakes.csv` | 记录培训错题 |
| `artifacts/incidents/incident_reviews.csv` | 记录事故复盘与整改信息 |

### 5.3 数据设计特点

当前数据设计采用“静态主库 + 轻量运行日志”的方式，优点包括：

1. 结构清晰，便于演示与调试；
2. 不依赖复杂数据库就能跑通闭环；
3. 便于将关键行为留痕；
4. 便于后续在不改变上层页面逻辑的情况下替换底层存储。

当前局限包括：

1. CSV 更适合展示期和中小规模运行，不适合复杂事务型生产场景；
2. 多角色权限与更细粒度审计能力尚未在当前版本中完全展开；
3. 大规模试点时可能需要更正式的数据层升级。

## 6. 关键业务链路设计

### 6.1 问答链路

当前正式问答链路设计目标是：**知识支撑优先，规则约束优先，自由生成从属于安全场景。**

#### 当前链路概念

```text
用户问题 -> 意图/风险判断 -> 正式知识问答链路（Dify） -> 返回结构化回答
                              \-> fallback（异常兜底）
```

#### 核心设计点

1. 正式实验室安全问答链路以 Dify 正式知识库工作流为准；
2. fallback 存在，但不是主卖点；
3. 回答强调安全结论、步骤、禁止事项和升级处理；
4. 高风险问题受规则层约束；
5. 低置信问题进入后续补强队列。

#### 当前设计取舍

为了保证展示稳定性，当前正式验收时采用的检索参数更偏保守：

1. `top_k = 3`
2. `reranking_enable = false`
3. `keyword_weight = 1.0`
4. `vector_weight = 0.0`

这说明当前稳定展示优先于“理想的混合检索完整配置”。

---

### 6.2 风险评估链路

风险评估链路的设计目标是：把实验场景转换为可执行的风险判断。

#### 输入

1. 用户问题
2. 实验场景描述
3. 涉及的试剂、设备、条件信息

#### 输出

1. 风险等级
2. 关键危险点
3. PPE 建议
4. 禁忌操作
5. 处置或控制建议

#### 当前实现思路

当前 `web_demo/app.py` 中维护了：

1. 风险等级标签；
2. PPE 提示词映射；
3. 危险类型提示词映射；
4. 与场景分析相关的基础数据结构。

这使风险评估输出不仅是自由文本，还能在一定程度上结构化。

---

### 6.3 准入阻断链路

准入阻断链路是当前系统区别于普通聊天机器人的关键设计。

#### 设计目标

将“建议”升级为“是否允许开工”的判定依据。

#### 核心流程

```text
当前问题/场景 -> 生成检查清单 -> 用户提交清单 -> 判断关键项是否满足 -> 输出允许/阻断结果
```

#### 当前实现要点

1. 系统可基于当前问题生成清单；
2. 当关键项未满足时，返回“暂不可开工”；
3. 结果及原因可记录到 `checklist_runs.csv`；
4. 页面展示上会明确“阻断”而不是普通建议。

#### 设计价值

1. 将安全要求从知识建议变成操作门槛；
2. 支撑“开工前把关”的业务表达；
3. 使平台价值从“能答问题”提升为“能拦风险”。

---

### 6.4 培训与统计链路

培训链路设计目标是：使平台不仅能回答问题，也能用于学习与准入。

#### 当前流程

```text
题库 -> 用户作答 -> 评分 -> 记录结果 -> 汇总为通过率/错题/薄弱项
```

#### 当前实现要点

1. 使用 `training_question_bank.json` 作为题库来源；
2. 训练结果写入 `training_attempts.csv`；
3. 错题信息写入 `training_mistakes.csv`；
4. 页面可展示培训通过率等统计信息。

#### 设计价值

1. 支撑从问答到培训的延伸；
2. 支撑管理员查看培训整体情况；
3. 支撑后续针对高频薄弱项优化知识库和培训内容。

---

### 6.5 事故复盘链路

事故复盘链路设计目标是：把安全管理从事前延伸到事后。

#### 当前流程

```text
事件记录 -> 原因分类 -> 整改措施 -> 责任人/截止日期 -> 状态更新 -> 复盘留痕
```

#### 当前实现要点

1. 使用 `incident_reviews.csv` 记录复盘与整改数据；
2. 支持标题、场景、严重程度、状态、责任人、截止时间等字段；
3. 页面上可作为管理闭环模块展示；
4. 当前在正式答辩主线中不默认展开完整流程，但属于正式模块范围。

## 7. 规则引擎设计

### 7.1 规则库结构

当前规则库分为两部分：

1. `global_policy`
2. `rules`

#### `global_policy` 负责

1. 默认动作；
2. 低置信动作；
3. 是否引用来源；
4. 安全回答模板。

#### `rules` 负责

1. 匹配类别；
2. 关键词模式；
3. 动作；
4. 严重程度；
5. 返回响应。

### 7.2 当前动作类型

当前规则动作主要包括：

1. `safe_answer`
2. `refuse`
3. `redirect_emergency`
4. `ask_for_more_info`

### 7.3 当前规则覆盖范围

当前规则重点覆盖：

1. 危险混合
2. 易燃溶剂明火加热
3. 不当危废处置
4. PPE 绕过
5. 通风柜绕过
6. 自伤/违法风险
7. Prompt 注入
8. 触电、火灾、化学品泄漏、误食、吸入、烫伤等应急场景

### 7.4 规则引擎价值

规则层的存在使得系统具备以下特征：

1. 不完全依赖模型自由发挥；
2. 高风险问题能快速受限；
3. 应急问题可优先返回规范模板；
4. 有利于后续扩展更细粒度的安全策略。

## 8. 知识治理与入库设计

### 8.1 当前目标

知识治理层设计目标是把多来源材料统一沉淀为兼容项目主知识库结构的数据。

### 8.2 已有两条主要入库路径

#### 路径 A：网页抓取与正文清洗

见：

- `docs/pipeline/web_ingestion_pipeline.md`

主要步骤：

1. 维护网页来源清单；
2. 抓取网页并留存结果；
3. 清洗正文并形成结构化内容；
4. 产出 `knowledge_base_web.csv`；
5. 需要时并入主知识库。

#### 路径 B：统一知识库入库入口

见：

- `docs/pipeline/unified_ingestion_pipeline.md`

主要步骤：

1. 输入 PDF / Word / PPT / 网页等来源；
2. 统一处理；
3. 产出兼容主知识库结构的 CSV；
4. 在复核后并入已有知识库。

### 8.3 当前知识治理设计特点

1. 支持多来源数据接入；
2. 支持先抽检、再合并；
3. 支持与现有知识库字段兼容；
4. 有利于后续逐步扩容，而不必一次性重构。

### 8.4 当前不足

1. 当前正式统一口径仍为 `398` 条，规模与申报书目标存在差距；
2. 条目级版本治理与 SLA 统计仍待补齐；
3. 当前仍偏展示期与迭代期，尚未形成完整的正式知识治理平台。

## 9. 接口与页面设计

### 9.1 页面设计目标

当前页面设计目标是：

1. 让评审能快速看到平台总价值；
2. 让主讲人按固定顺序稳定演示；
3. 让个人问答价值与管理价值都能被看见。

### 9.2 当前主页面结构

当前稳定主线围绕以下页面模块展开：

1. 平台总览
2. 智能问答
3. 准入阻断
4. 培训与看板
5. 指标收口

### 9.3 当前页面设计原则

1. 不追求页面数量多，而追求主线稳定；
2. 不要求所有模块现场都完整展开；
3. 默认不从后台配置页、部署页开始；
4. 默认不在现场展开事故复盘完整录入流程；
5. 页面只是承载业务链路，不把 UI 花哨作为核心卖点。

## 10. 性能与可靠性设计

### 10.1 当前性能真实情况

根据正式验收材料：

1. 正式回归 `20/20`
2. 三轮稳定性 `3/3 PASS`
3. 当前最大剩余问题是尾部延迟波动

### 10.2 当前性能优化动作

当前已经做过的优化包括：

1. 保持检索逻辑不变，优先保证正确率；
2. 下调 `max_tokens`；
3. 通过探针验证缩短输出长度对延迟有帮助。

### 10.3 当前可靠性设计

当前可靠性更多体现在“展示级稳定性”而非“生产级高可用性”，包括：

1. 正式回归与稳定性验证；
2. 浏览器级主线走查；
3. 演示脚本冻结与现场切换规则；
4. fallback 兜底；
5. 答辩材料统一口径。

### 10.4 当前限制

当前仍不能把系统描述为“已完全达到正式上线标准”，原因包括：

1. 尾延迟仍有波动；
2. prod readiness 不是当前首要目标；
3. 技术配置仍优先服务稳定展示。

## 11. 关键设计取舍

### 11.1 为什么先做展示闭环，而不是先做完整平台

因为当前阶段目标是课程 / 大创展示优先，需要先把价值链路讲清楚并稳定复现。

### 11.2 为什么先使用云端能力

因为这样更利于快速验证知识库、页面、规则与评测体系；后续待整体收敛后再评估本地化切换。

### 11.3 为什么当前数据层以 CSV 为主

因为当前更强调：

1. 可维护；
2. 可审核；
3. 可快速迭代；
4. 可直接支撑展示与材料整理。

### 11.4 为什么当前正式检索参数较保守

因为当前阶段优先保证正确率和展示稳定性，而不是一次性追求理想的复杂检索配置。

## 12. 当前设计约束

### 12.1 业务约束

实验室安全属于高约束场景，系统必须偏保守、偏规范，不能追求“看起来聪明”而牺牲安全边界。

### 12.2 时间约束

当前阶段服务于答辩与材料提交，不适合进行大规模高风险重构。

### 12.3 资源约束

当前项目团队与环境更适合采用“逐步补证据、逐步扩容量、逐步完善文档”的推进方式。

## 13. 后续设计扩展点

在不改变当前主展示基线的前提下，后续优先扩展以下方向：

1. 知识库扩容到阶段目标 `1200` 条，再冲 `3000+`
2. 检索链路恢复到更完整的混合检索/重排能力，并做稳定验证
3. 建立三类角色权限矩阵和更正式的 RBAC 设计
4. 建立知识更新 SLA、版本治理和条目级追踪
5. 建立试点用户、满意度、可用性、应用效果报告的数据采集与分析机制
6. 如条件成熟，再推进本地化模型替代或多模态扩展
