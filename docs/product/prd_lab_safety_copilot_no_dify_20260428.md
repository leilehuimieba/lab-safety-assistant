# Lab Safety Copilot PRD（no-Dify 自研轻量版）

> 日期：2026-04-28  
> 当前定位：暂停申报书主线，暂停 Dify 核心依赖，重新对接用户需求  
> 产品名称建议：**Lab Safety Copilot / 实验前安全检查助手**  
> 适用项目：`D:\newwork\lab-safe-assistant-workspace\lab-safe-assistant-github`

## 1. 产品定位

本项目不再定位为“基于 Dify 的 RAG 问答系统”，而重新定位为：

> 面向高校实验教学和科研实验的轻量级实验前安全检查助手。学生在开工前输入实验内容，系统自动识别风险、生成检查清单、判断是否需要阻断，并把高风险事项提交给老师确认。

它不是完整 EHS 平台，不是库存管理系统，也不是普通 AI 聊天机器人。

它要补足的是：

```text
现有安全平台偏后台合规，普通 AI 问答偏一问一答，二者都没有很好解决“学生准备开工前 5 分钟到底能不能做”的即时决策问题。
```

## 2. 为什么不再把 Dify 当核心依赖

当前项目是 vibe coding 快速迭代，Dify 会带来额外成本：

1. 需要配置平台、知识库、workflow、token。
2. 需要处理导入、发布、版本和链路异常。
3. 后续如果通过 MCP 或自动化操作平台，复杂度进一步上升。
4. 代码行为一部分藏在平台里，不利于测试、复现和快速改动。
5. 项目核心价值不是“接入 Dify”，而是“实验前风险判断和老师确认闭环”。

因此新路线：

```text
FastAPI + 本地知识库 + 规则引擎 + 模型直连 + 本地测试
```

Dify 可以保留为历史 demo 或可选 backend，但不作为 MVP 必选依赖。

## 3. 市场和竞品空缺

### 3.1 综合 EHS 平台

特点：功能完整，覆盖培训、检查、库存、隐患、报表、权限、SSO。

不足：

- 部署重；
- 更偏管理者；
- 学生开工前即时判断体验弱；
- 单实验室 / 单课程试点成本高。

### 3.2 库存 / SDS 管理系统

特点：擅长试剂库存、SDS、条码、采购和台账。

不足：

- 解决“有什么试剂”，不直接解决“今天这个实验能不能做”；
- 对老师审核和学生自查支持有限。

### 3.3 AI 安全问答

特点：能根据知识库回答问题。

不足：

- 容易停留在一问一答；
- 不主动追问缺失条件；
- 不生成开工检查单；
- 不做阻断；
- 不沉淀老师审核记录。

### 3.4 培训考试系统

特点：能证明学生是否培训过。

不足：

- 培训通过不等于具体实验可以安全开工；
- 场景化判断不足。

## 4. 目标用户

### 4.1 学生 / 新进实验人员

痛点：

- 不知道实验前该检查什么；
- SOP/SDS 看不懂或不愿看；
- 不知道哪些是必须禁止，哪些只是提醒；
- 出现不确定情况时不知道是否必须问老师。

需要：

- 输入实验场景后得到风险等级；
- 得到开工前检查清单；
- 明确知道是否需要老师确认；
- 遇到事故能看到应急卡片。

### 4.2 老师 / 助教

痛点：

- 重复提醒学生安全注意事项；
- 高风险实验缺少统一审核摘要；
- 学生是否真的理解风险不清楚；
- 缺少轻量记录。

需要：

- 查看待审核实验；
- 看到高风险摘要和缺失项；
- 快速批准 / 驳回 / 要求补充；
- 导出记录。

### 4.3 实验室管理员 / 安全员

痛点：

- 安全资料分散；
- 低置信问题没人沉淀；
- 高风险场景和阻断原因缺少统计；
- 培训和实际操作脱节。

需要：

- 查看风险热点；
- 查看低置信问题队列；
- 发现缺失 SOP / SDS；
- 导出周报。

## 5. MVP 核心场景

### 场景 1：实验前风险自查

输入：

- 实验名称；
- 试剂；
- 设备；
- 操作步骤；
- 是否阅读 SOP；
- 是否查看 SDS；
- PPE 是否齐全；
- 是否老师批准。

输出：

- 风险等级；
- 关键危险点；
- 缺失信息；
- 阻断原因；
- 开工结论：`允许 / 需老师确认 / 暂不可开工`。

### 场景 2：自动生成开工检查单

系统根据实验内容生成检查项：

- SOP 已阅读；
- SDS 已查看；
- PPE 已确认；
- 通风 / 防火 / 应急设备已确认；
- 废液去向已确认；
- 老师批准已确认。

### 场景 3：老师审核包

高风险提交生成摘要：

- 学生 / 实验；
- 风险等级；
- 缺失项；
- 系统建议；
- 老师操作：批准、驳回、要求补充。

### 场景 4：安全问答带来源

用户提问时系统从本地知识库检索，并回答：

- 处理步骤；
- 禁止事项；
- 来源；
- 不确定时提示联系老师。

### 场景 5：低置信问题队列

如果系统无法可靠回答：

- 不硬答；
- 进入待补知识队列；
- 管理员可标记负责人和状态。

### 场景 6：管理看板

展示：

- 今日待审核；
- 高风险实验数量；
- 阻断原因 Top 5；
- 低置信问题；
- 高频安全问题。

## 7. 不做范围

MVP 不做：

1. 不做完整 EHS 平台。
2. 不做全校组织架构。
3. 不做正式 SSO。
4. 不做全量危化品库存。
5. 不做采购审批。
6. 不做门禁联动。
7. 不做 IoT 实时监控。
8. 不强制接入 Dify。
9. 不让 AI 直接承担最终安全许可。

## 8. 技术路线

建议 MVP 技术栈：

```text
后端：FastAPI
前端：现有 HTML/JS 先复用，必要时再迁移 React/Vite
数据：SQLite + CSV/JSON 种子数据
知识库：本地 Markdown/CSV/SOP 片段
检索：关键词 + rapidfuzz/SQLite FTS，后续可选 embedding
模型：OpenAI-compatible API 直连，可切本地模型
规则：YAML/JSON 安全规则
测试：pytest + 场景测试集
```

核心链路：

```text
实验场景输入
  ↓
规则引擎识别硬阻断
  ↓
本地知识库检索
  ↓
模型生成风险摘要 / 检查单
  ↓
规则二次校验
  ↓
输出：允许 / 需老师确认 / 暂不可开工
  ↓
记录到老师工作台和管理看板
```

## 9. 验收指标

| 指标 | MVP 目标 |
|---|---|
| 高风险阻断正确率 | 核心测试场景 ≥90% |
| 危险答案放行数 | 0 |
| 检查单生成可用率 | ≥90% |
| 来源引用率 | 专业问答 ≥80% |
| 低置信兜底率 | 知识不足时不硬答，进入队列 |
| 老师审核包可读性 | 老师能在 30 秒内看懂风险和缺失项 |
| 本地运行 | 不依赖 Dify 即可完成主链路 |

## 10. 第一轮开发建议

第一轮只做一个完整闭环：

```text
实验前自查表单
  -> 风险等级
  -> 检查单
  -> 阻断结论
  -> 老师审核包
  -> 管理看板统计
```

不要先做：

- 大模型复杂编排；
- Dify 迁移；
- 3000 条知识库；
- SSO；
- UI 大重构。

## 11. 推荐演示脚本

1. 学生输入一个高风险实验，例如锂电池拆解或易燃溶剂加热。
2. 系统输出高风险，生成检查单。
3. 学生故意不勾选 SOP/SDS/PPE/老师批准。
4. 系统显示：暂不可开工，必须联系老师。
5. 老师工作台出现一条待审核记录。
6. 老师看到摘要：风险、缺失项、建议动作。
7. 管理看板显示阻断原因和高风险场景。

一句话收口：

> 我们不是做一个普通 AI 问答页，而是把实验前安全判断变成可操作、可阻断、可提交老师确认的轻量闭环。
