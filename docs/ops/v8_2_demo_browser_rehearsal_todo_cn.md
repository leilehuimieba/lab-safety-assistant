## 3. 必测项：T10-1 必须重点记录

### B1. 开场是否直接从 `web_demo` 开始

需要记录：
- 是否直接从 `web_demo` 开始
- 主讲人是否能在 15 - 20 秒内完成首页总览
- 是否还有切回 README 的冲动或必要

通过标准：
- 直接从 `web_demo` 开场明显更顺
- 不需要 README 才能把项目讲清楚

### B2. 问答是否能在浏览器里稳定展示

需要记录：
- 主问题是否成功提交
- 浏览器里是否能在 **15 秒内** 返回有效结果
- 当前页面展示的是 Dify 正式链路，还是 fallback 结果
- 主讲人在看到 fallback 时，是否还能按当前口径稳定解释

通过标准：
- 问答能稳定展示
- 若走 fallback，也不会导致现场主线崩掉

### B3. 阻断是否足够稳定

需要记录：
- 清单是否能成功生成
- 故意保留一个关键项不勾选后，是否能稳定触发阻断
- 主讲人是否能用一句话讲清“从能答到能拦”

通过标准：
- 阻断结果稳定出现
- 阻断原因和下一步建议在页面上可见

### B4. 看板是否足够快

需要记录：
- 看板刷新是否顺
- 是否能在 40 - 60 秒内指出：
  - 清单阻断率
  - 培训通过率
  - 低置信问题
  - 最近高风险场景

通过标准：
- 不需要逐个数字解释
- 主讲人能快速完成“平台不只服务问答，还服务管理”的表达

### B5. 事故复盘是否继续只作扩展

需要记录：
- 本轮是否展示事故复盘
- 若展示，是否有现成记录可用
- 若不展示，评审是否仍能理解闭环概念

通过标准：
- 即使不展示事故复盘，主线也完整
- 若展示，不会拖慢整体节奏

### B6. 总时长是否压得住

需要记录：
- 实际总时长
- 哪一步最耗时
- 哪一步最卡
- 是否需要切 3 分钟版

通过标准：
- 默认主线能控制在 `4.5 - 5 分钟`

## 4. 建议的彩排执行顺序

按当前正式上台默认主线执行：

1. `web_demo` 首页总览
2. 问答
3. 开工前检查清单
4. 管理端看板
5. 指标收口

仅在“时间充足 + 有现成记录”时，才额外观察事故复盘。

## 5. 本轮彩排最值得重点盯的风险

结合 API 预检，当前最值得盯的风险不是服务挂掉，而是：

1. **浏览器里问答虽然能返回，但实际展示的是 fallback，不是 Dify 正式链路**
2. **主讲人是否能在 fallback 情况下仍然把口径讲稳**
3. **看板虽然接口可用，但现场讲解是否会拖时**
4. **事故复盘当前无记录，若强行演示容易拖慢节奏**
