# 实验室安全小助手答辩口径总表

> 用途：作为当前课程 / 大创展示阶段的统一答辩入口。  
> 优先级：答辩话术、3 分钟脚本、根 README 如有冲突，以本文为准。  
> 当前基线：`v8.2`

## 1. 一句话定位

“实验室安全小助手是一个面向高校实验室场景的安全智能辅助系统，当前重点不是泛化聊天，而是把实验室安全问答、风险评估、开工前检查、培训考核、管理看板和事故复盘串成一个可演示、可解释、可复现的闭环原型。”

## 2. 当前必须统一的项目口径

### 2.1 项目名称
- 正式项目名：实验室安全小助手
- 英文名：Lab Safety Assistant

### 2.2 项目定位
- 当前阶段：课程 / 大创展示优先
- 当前目标：可演示、可答辩、可继续扩展
- 当前不是首要目标：prod 正式上线

### 2.3 当前展示基线
- 当前展示基线版本：`v8.2`
- 当前答辩主页面：`web_demo`
- 实验室安全问答唯一正式链路：Dify 正式知识库工作流
- 页面中的结构化 fallback：仅用于链路异常兜底，不作为主卖点

## 3. 当前可以稳定宣讲的核心能力

以下能力已经在现有页面、接口或验收文档中有直接对应证据，答辩时可以稳定讲：

1. 实验室安全问答  
   - 支持基于知识库的回答
   - 支持引用知识条目
   - 高风险问题有规则约束
   - 低置信问题会进入后续补强队列

2. 风险评估  
   - 可根据实验场景给出风险等级、关键危险点和防护建议

3. 开工前检查与阻断  
   - 可根据场景生成检查清单
   - 关键项不满足时可阻断开工

4. 培训考核与统计  
   - 支持题库、作答、评分、通过率统计

5. 管理端看板  
   - 可展示清单阻断率、培训通过率、低置信问题、高风险场景和事故摘要

6. 事故复盘  
   - 支持事件记录、整改责任、整改时限、状态更新和逾期提醒

## 4. 当前统一指标口径

答辩材料统一使用以下指标：

- 知识库正式导入：`398` 条成功
- 20 题正式回归：`20/20`
- 连续 3 轮真实回归：`3/3 PASS`
- 当前状态：可演示、可答辩、可继续扩展

## 5. 当前性能口径

必须统一这样表述：

1. 正确率已稳定达标
2. 演示可用性已达标
3. 延迟已明显下降，但仍有波动
4. 当前最大的剩余问题不是回答正确性，而是尾部延迟波动

不建议在答辩中自行扩展为：
- “已经达到生产可上线”
- “已经完全稳定可商用”
- “延迟问题已经彻底解决”

## 6. 当前推荐的模块价值讲法

### 问答
解决“查不到、问不清”的问题。

### 风险评估
把实验场景翻译成可执行的风险点和防护建议。

### 开工前检查
把“建议”升级成“阻断条件”。

### 培训考核
让系统不仅能答，还能用于训练和准入。

### 管理看板
让老师 / 管理员看到整体风险趋势，而不是只看单条回答。

### 事故复盘
把安全管理从事前延伸到事后闭环。

## 7. 当前不要超讲的内容

以下内容如果没有现场证据，不建议当作“已完成能力”来讲：

1. 大规模校内真实部署
2. 已在多个实验室长期稳定运行
3. 完整的正式管理平台落地
4. 已经切换为本地模型并稳定运行
5. prod 环境已完全通过正式上线门禁

这些内容可以讲成：
- 下一阶段方向
- 条件成熟后的扩展计划
- 已有路线，但当前仍在展示 / 验证阶段

## 8. 评委高频问题统一回答方向

### 8.1 和普通 AI 聊天有什么区别？
“我们不是只做自由问答，而是把知识库、规则约束、开工检查、培训统计和事故复盘串起来，形成实验室安全闭环。”

### 8.2 为什么不只做聊天机器人？
“因为实验室安全不是知道答案就够了，还要落实到开工前阻断、培训准入、风险统计和整改闭环。”

### 8.3 当前最真实的短板是什么？
“当前最主要的短板不是功能缺失，而是高价值正式知识源仍需继续扩容，同时尾部延迟还需要继续压缩波动。”

### 8.4 为什么先用云端模型？
“先用云端模型是为了快速验证链路、页面、知识库和评测体系，等整体收敛后再切本地模型，风险更可控。”

## 9. 当前推荐的收尾口径

“我们当前交付的不是一个泛化聊天机器人，而是一个可演示的实验室安全闭环原型。它已经把问答、风险评估、开工阻断、培训统计、管理看板和事故复盘串了起来。下一阶段我们会继续扩充高价值正式知识源、进一步压缩延迟波动，并在条件成熟后推进更强的本地化部署能力。”
